# BDC Web 4.0 前端编码规范

## 1. 适用范围

本规范适用于本项目 `src` 目录下新增和修改的 Vue、TypeScript、Less/CSS 代码。

项目技术栈：Vue 3、TypeScript、Vite、Pinia、Vue Router、Ant Design Vue、Axios、Less。

本规范依据现有工程结构和代表性代码整理。历史代码存在风格不一致时，新增代码按本文执行；修改历史文件时，在不扩大改动范围的前提下逐步统一。

## 2. 基本原则

1. 保持简单：一个模块只承担清晰、单一的职责。
2. 类型优先：能明确类型时不使用 `any`，公共数据结构必须声明类型。
3. 复用优先：请求、弹窗、抽屉、表格、字典、缓存等能力优先使用项目现有封装。
4. 最小改动：业务修改不得顺带大面积格式化无关代码。
5. 可读性优先：变量、函数和组件名称应表达业务含义，避免无意义缩写。
6. 安全优先：不得提交账号、密码、Token、私钥或生产环境地址等敏感信息。

## 3. 文件与目录

### 3.1 目录职责

| 目录 | 职责 |
| --- | --- |
| `src/api` | 后端接口及接口数据模型 |
| `src/assets` | 图片、SVG、Less 等静态资源 |
| `src/components` | 可复用公共组件 |
| `src/directives` | Vue 自定义指令 |
| `src/enums` | 枚举和稳定常量 |
| `src/hooks` | Composition API 复用逻辑 |
| `src/router` | 路由、路由守卫和路由辅助方法 |
| `src/settings` | 项目级配置和初始化逻辑 |
| `src/store` | Pinia 状态管理 |
| `src/utils` | 无界面依赖的通用工具 |
| `src/views` | 按业务模块组织的页面和页面私有组件 |
| `types` | 全局及跨模块 TypeScript 声明 |

页面私有组件放在当前业务目录的 `components` 下；只有被多个业务模块复用的组件才放入 `src/components`。

### 3.2 文件命名

- Vue 组件使用 PascalCase，如 `UserModal.vue`、`SvgIcon.vue`。
- 路由页面入口可沿用 `index.vue`；同一目录中不得出现含义不清的多个 `index` 变体。
- TypeScript 工具、API、store、hook 文件使用 camelCase，如 `userModel.ts`、`routeHelper.ts`、`useThemeSetting.ts`。
- Hook 必须以 `use` 开头。
- 类型模型文件建议以 `Model.ts` 或 `model.ts` 结尾，同一模块内保持一致。
- 禁止新增 `_copy`、`新建文件`、`test1` 等临时命名；实验代码不得进入正式目录。

## 4. 格式与编码

- 所有文本文件使用 UTF-8 编码，统一使用 LF 换行。
- 使用 2 个空格缩进，禁止 Tab 与空格混用。
- TypeScript/JavaScript 默认使用单引号。
- 默认不写行末分号；同一文件必须保持一致。
- 运算符、逗号后保留空格；对象字面量花括号内保留空格。
- 单行过长时按参数、属性或调用链合理换行，模板标签也应拆分属性。
- 文件末尾保留一个空行，不保留行尾空格。
- 中文注释必须正常可读。发现乱码应先确认原始编码，禁止复制乱码形成新注释。

推荐后续补充 ESLint、Prettier 和 EditorConfig；在自动化规则落地前，以本文为准。

## 5. TypeScript 规范

### 5.1 类型声明

- 项目开启了 `strict`，新增代码必须通过 TypeScript 类型检查。
- 对外暴露的函数、组件 Props/Emits、API 参数与返回值必须有明确类型。
- 数据对象优先使用 `interface`，联合类型、工具类型和别名使用 `type`。
- 类型、接口、枚举、组件使用 PascalCase；变量和函数使用 camelCase；常量使用 UPPER_SNAKE_CASE。
- 布尔变量使用 `is`、`has`、`can`、`should` 等前缀。
- 禁止用 `Boolean`、`String`、`Number`、`Object` 等包装类型，使用 `boolean`、`string`、`number` 和明确对象类型。
- 避免非空断言 `!` 和强制类型转换；确有必要时说明原因。

```ts
interface UserFormData {
  id?: string
  username: string
  enabled: boolean
}

type SaveMode = 'add' | 'edit'
```

### 5.2 `any` 使用

- 禁止为了省事使用 `any`。
- 第三方库缺少类型时优先补充声明；暂时无法确定的数据使用 `unknown` 并做类型收窄。
- 若历史接口只能使用 `any`，应将其限制在接口适配层，不得向页面和公共组件扩散。

### 5.3 变量与函数

- 默认使用 `const`，仅在变量需要重新赋值时使用 `let`，禁止使用 `var`。
- 函数名使用动词或动宾结构，如 `loadUserList`、`handleSubmit`、`validateForm`。
- 事件处理函数统一使用 `handleXxx`；数据加载可使用 `loadXxx`/`fetchXxx`；状态更新使用 `setXxx`。
- 函数尽量只做一件事；复杂分支拆为具名函数，减少深层嵌套。
- 未使用的参数、导入和变量必须删除，不以注释方式长期保留。
- 比较统一使用 `===` 和 `!==`，仅判断 `null` 与 `undefined` 时可明确使用空值判断。
- 优先使用可选链 `?.` 和空值合并 `??`，不要用 `||` 覆盖合法的 `0`、`false` 或空字符串。

## 6. Vue 单文件组件

### 6.1 组件结构

统一采用 Vue 3 Composition API 和 `<script setup lang="ts">`：

```vue
<template>
  <!-- 页面结构 -->
</template>

<script setup lang="ts">
// 导入、类型、props/emits、状态、计算属性、监听、生命周期、方法
</script>

<style scoped lang="less">
/* 当前组件样式 */
</style>
```

脚本内部建议按以下顺序组织：

1. 外部库、项目模块和类型导入；
2. 类型与常量；
3. `defineProps`、`defineEmits`、`defineExpose`；
4. 响应式状态和模板引用；
5. `computed`、`watch`；
6. 生命周期；
7. 事件处理和业务方法。

### 6.2 Props 与 Emits

- 新增组件优先使用类型式 `defineProps` 和 `withDefaults`。
- Props 视为只读，禁止直接修改对象型 Props；编辑表单应创建本地副本，保存时通过事件回传。
- 数组和对象默认值必须使用工厂函数，禁止 `default: []`、`default: {}`。
- Emits 必须声明事件名和参数类型。
- 双向绑定遵循 `modelValue` + `update:modelValue` 约定。
- 事件名在模板中使用 kebab-case，如 `@refresh-list`。

```ts
interface Props {
  open?: boolean
  dataInfo?: UserFormData
}

const props = withDefaults(defineProps<Props>(), {
  open: false,
  dataInfo: () => ({ username: '', enabled: true })
})

const emit = defineEmits<{
  ok: [data: UserFormData]
  cancel: []
}>()
```

### 6.3 响应式状态

- 基础值、可整体替换的数据和 DOM/组件引用使用 `ref`。
- 结构稳定且按属性修改的对象可使用 `reactive`。
- 模板中使用的派生状态使用 `computed`，不要用 `watch` 手动同步可计算出的值。
- `watch` 必须明确数据源和副作用，避免无必要的 `deep: true`。
- 定时器、事件监听器和第三方实例必须在 `onBeforeUnmount`/`onUnmounted` 中清理。
- 模板引用命名应表达用途，如 `formRef`、`tableRef`，不要使用 `link`、`dom1` 等模糊名称。

### 6.4 模板

- 组件标签统一使用 kebab-case，属性较多时一行一个或按逻辑分组换行。
- `v-for` 必须设置稳定且唯一的 `:key`，禁止默认使用数组下标。
- 避免在模板中编写复杂表达式、长链式调用和数据转换，提取为 `computed` 或方法。
- `v-if` 用于是否渲染，`v-show` 用于频繁切换显示状态。
- 同一元素避免同时使用 `v-if` 与 `v-for`。
- Ant Design Vue 双向绑定按组件 API 使用，如 `v-model:value`、`v-model:open`、`v-model:checked`。

## 7. 组件设计与通信

- 公共组件应保持通用，不直接依赖具体业务 API、路由或 store。
- 父组件通过 Props 下发数据，子组件通过 Emits 上报事件。
- 仅在弹窗、表单等确需命令式调用的场景使用 `defineExpose`，且只暴露最小 API。
- 跨层级但局部的数据可使用 `provide/inject`；全局业务状态进入 Pinia。
- 不以修改 Props、访问子组件内部 `$` 属性等方式形成隐式耦合。
- 复用项目已有的 `cModal`、`cDrawer`、表格、图标和全局组件，避免重复实现相同能力。

## 8. API 与异步请求

- API 按业务域放入 `src/api/<domain>`，接口模型放入对应 `model` 目录。
- 统一使用项目的 `defHttp`，页面组件不得自行创建 Axios 实例。
- 地址集中定义在 `Api` 枚举或常量对象中，名称表达动作和资源。
- GET 查询参数使用 `params`，POST/PUT 请求体使用 `data`。
- 请求参数、响应数据和函数返回值必须声明类型。
- 优先使用 `async/await`，同一函数内不要混用 `await` 与多层 `.then()`。
- 不要为已有 Promise 再包一层无意义的 `new Promise`。
- 错误必须有明确处理：用户可感知的问题给出提示，技术错误交由统一请求层或日志模块处理。
- 禁止吞掉异常、只返回 `null` 而不区分失败原因；必要时抛出业务错误或返回明确的结果类型。
- Token 由统一请求层处理，业务请求不得重复拼装认证头，特殊匿名请求明确设置 `withToken: false`。
- URL 参数使用 `params` 或 `URLSearchParams`，禁止直接拼接未经编码的用户输入。

```ts
enum Api {
  UserList = '/api/zrzy-system/sys/v1/user/list',
  SaveUser = '/api/zrzy-system/sys/v1/user/save'
}

export function getUserList(params: UserListParams) {
  return defHttp.get<UserListResult>({ url: Api.UserList, params }, { withToken: true })
}
```

## 9. Pinia 状态管理

- Store 按业务域拆分到 `src/store/modules`，ID 使用稳定且唯一的 kebab-case 名称。
- State 必须声明接口并提供与类型一致的初始值，避免 `string` 字段初始化为 `false` 等类型漂移。
- Getter 只做派生计算，不产生副作用。
- Action 负责状态变更及相关业务流程；页面不得随意修改其他模块的内部状态。
- 持久化缓存统一通过项目缓存/认证工具处理，不在业务页面散落 `localStorage` 操作。
- Store 外使用项目既有的 `useXxxStoreWithOut` 模式时保持模块一致。

## 10. 路由规范

- 路由配置使用项目的 `AppRouteRecordRaw` 类型。
- `path` 使用 kebab-case；`name` 使用 PascalCase，并保持全局唯一。
- 页面组件使用动态导入：`() => import('/@/views/...')`。
- 路由标题、菜单隐藏、面包屑等信息统一放在 `meta`。
- 登录、权限、异常跳转等公共逻辑放入路由守卫，不分散在普通业务页面。
- 新增路由时同步检查菜单、权限、缓存和刷新场景。

## 11. 样式规范

- 组件私有样式使用 `<style scoped lang="less">`。
- 全局主题、Ant Design Vue 覆盖和通用样式放在 `src/assets/less`，不得在业务组件中无范围覆盖全局类。
- 类名使用 kebab-case，并以页面或组件名作为作用域前缀，如 `.sys-user__toolbar`。
- 优先使用 class，避免大量内联 `style`。
- 颜色、字号、间距等重复值应复用主题变量或公共变量，避免散落魔法值。
- `!important` 仅用于确实无法通过选择器层级解决的第三方组件覆盖，并写明原因。
- 布局优先使用 Flex/Grid，避免依赖大量绝对定位。

## 12. 注释、日志与错误处理

- 注释说明“为什么这样做”及业务限制，不复述代码本身。
- 公共函数、复杂算法和特殊业务规则使用简洁的 JSDoc。
- 删除失效的大段注释代码；历史实现应由 Git 保存。
- 禁止提交无用途的 `console.log`、`console.info`、`debugger`。
- 必须记录的异常使用项目日志工具，并避免输出 Token、密码、身份证号等敏感数据。
- 用户提示统一使用 Ant Design Vue 的 `message`、`notification` 或 `Modal`，提示语应清晰且可操作。

## 13. 安全规范

- 密码、Token、密钥、许可证、公私钥等不得硬编码在前端源码中。
- `.env` 中只允许存放可公开的前端构建配置；前端环境变量会被打包，不属于秘密存储。
- 所有用户输入在展示、拼接 URL、生成 HTML 或提交前按场景校验和编码。
- 慎用 `v-html`；必须使用时确保内容来自可信来源或经过严格净化。
- 权限控制不能只依赖按钮隐藏，后端必须同步校验。
- 上传文件应校验类型、大小和数量，不信任文件扩展名。

## 14. Git 与提交

- 一次提交只处理一个主题，避免混入无关格式化和生成文件。
- 提交信息建议使用：`类型(模块): 简要说明`。
- 常用类型：`feat`、`fix`、`refactor`、`style`、`docs`、`test`、`chore`。
- 禁止提交 `node_modules`、`dist`、日志、临时文件、IDE 私有配置和真实环境密钥。

示例：

```text
feat(user): 增加用户部门懒加载选择
fix(router): 修复刷新后动态路由丢失
```

## 15. 提交前检查清单

- [ ] 文件编码为 UTF-8，中文和注释无乱码。
- [ ] 命名准确，无临时文件、复制文件和无意义缩写。
- [ ] 新增代码无不必要的 `any`，Props、Emits、API 均有类型。
- [ ] 对象/数组 Props 默认值使用工厂函数，且没有直接修改 Props。
- [ ] `v-for` 使用稳定的 `key`，模板中无复杂业务表达式。
- [ ] 请求统一通过 `defHttp`，异常和用户提示处理完整。
- [ ] 定时器、监听器和第三方实例已在卸载时清理。
- [ ] 无调试日志、`debugger`、废弃注释代码和敏感信息。
- [ ] 样式作用域正确，无无依据的 `!important` 和全局污染。
- [ ] 执行 `yarn build-1`（完整类型检查与构建）或至少执行 `yarn build`，并处理本次改动引入的问题。

## 16. 当前项目重点治理项

以下问题在历史代码中已有出现，新增代码不得继续引入，修改相关模块时应逐步治理：

1. 中文注释或字符串乱码；
2. 单双引号、分号和缩进风格混用；
3. 大量 `any`、缺少函数参数和接口响应类型；
4. `default: []`、`default: {}` 等共享引用 Props 默认值；
5. 直接修改对象型 Props；
6. 多层 `.then().catch()`、无意义 `new Promise` 和吞异常；
7. `==`/`!=`、无效可选链和类型不一致的状态值；
8. 业务组件直接操作 `localStorage`、认证头或跨组件内部实例；
9. 遗留 `console.log`、注释代码和硬编码配置；
10. 超大 Vue 文件同时承担模板、请求、状态和复杂业务逻辑。

对超大组件应按“页面容器、业务子组件、API、类型、hook/工具”逐步拆分，但不得在普通需求中一次性重写整个历史模块。
